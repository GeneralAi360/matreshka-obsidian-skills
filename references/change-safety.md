## Режимы операции

Классифицировать запрос до работы:

| Режим | Примеры | Право записи |
|---|---|---|
| audit | анализ дерева, lint, поиск дублей | нет |
| additive | новая заметка, новый отчёт | только новые точные пути |
| bounded edit | локальная правка существующей заметки | минимальный patch после baseline |
| structural | move, rename, merge, split, migration | только после плана, backup и подтверждения |
| destructive | delete, purge, overwrite, очистка | запрещено без прямого точного запроса |

Если запрос допускает несколько режимов, выбрать менее разрушительный.

## Обязательный preflight

До любой записи:

1. Проверить точный vault root.
2. Прочитать применимые инструкции и ограничения.
3. Зафиксировать top-level tree, количество и типы файлов.
4. Проверить Git status или другой механизм восстановления.
5. Найти совпадения по имени, `id`, aliases и ссылкам.
6. Создать baseline inventory вне vault.
7. Назвать точные пути, которые предполагается изменить.
8. Отделить детерминированные изменения от смысловых решений.

Не использовать `*`, `**`, unresolved variables или домашний каталог как цель destructive-команды.

## Запрещённые действия по умолчанию

Без отдельного точного решения пользователя не:

- удалять заметки, папки или вложения;
- очищать Trash или архив;
- заменять существующий каталог новой структурой;
- переносить содержимое неподходящей папки «туда, где должно быть»;
- сливать похожие заметки;
- удалять неизвестные properties;
- переписывать все ссылки после предполагаемого rename;
- преобразовывать все Markdown-файлы одним форматтером;
- перезаписывать существующий файл командой с `overwrite`;
- изменять immutable Raw;
- выполнять массовую миграцию только потому, что lint показал legacy-path.

Предложение Matreshka OS является сопоставлением, а не разрешением переделывать сторонний vault.

## Условия структурного изменения

Разрешить structural-операцию только когда выполнены все условия:

1. пользователь подтвердил цель и точные пути;
2. показан список создаваемых, изменяемых, перемещаемых и удаляемых объектов;
3. существует проверенный recoverable backup или история версий;
4. нет неразрешённого параллельного изменения тех же файлов;
5. известны backlinks, embeds, Bases, Maps, Templates и scripts, зависящие от путей;
6. подготовлена процедура rollback;
7. выбран способ проверки результата.

Отсутствие backup является stop condition. Не считать копию в том же изменяемом каталоге полноценным backup.

## Безопасный перенос

Вместо move-first использовать copy-verify-retire:

1. Скопировать содержимое в новый точный путь без удаления исходника.
2. Сверить размер, hash и содержимое.
3. Обновить ссылки минимальным patch.
4. Повторить lint и проверить Obsidian.
5. Показать пользователю результат.
6. Переместить исходник в recoverable archive или удалить его только после отдельного подтверждения.

Для merge:

- сохранить обе исходные заметки до review;
- перечислить, какое утверждение пришло из какого файла;
- не менять стабильные `id` молча;
- использовать superseded/redirect-механику из локальной Schema.

## Проверка после записи

Сравнить before/after inventory:

- missing path без разрешения — error;
- изменение нецелевого файла — error;
- изменение Raw — error;
- новый файл вне разрешённого scope — warning или error;
- изменение Private при неразрешённом scope — error;
- изменение `id` — error;
- потеря property, секции или attachment — error до объяснения.

При любой неожиданной потере остановиться. Не продолжать следующую миграционную фазу.
